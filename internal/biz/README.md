# Biz

## 分层定位

当前服务采用 Kratos 分层架构，并按应用编排 + 领域能力的方式组织业务：

- 应用层：`SeckillUsecase` 负责编排完整流程，包括限流、幂等、缓存、消息、事务和补偿。
- 领域能力层：活动与商品查询、库存预占与确认、订单创建与支付、用户券核销、订单取消与补偿。
- 基础设施层：MySQL、Redis、Kafka、延迟队列和可观测组件由 repo/job/kafka/observability 提供。

`SeckillUsecase` 不直接代表单个领域对象，它更像应用服务：把多个领域能力组合成一次可靠的交易流程。

## 用户券生命周期

用户券链路按营销资产生命周期处理：

1. 发放：`GrantCouponByReview` 根据评价场景创建用户券实例，使用 `idempotency_key` 防止重复发券。
2. 持有：用户券存储在 `user_coupon`，记录归属用户、券模板、场景、状态和过期时间。
3. 下单核销：创建订单时传入 `user_coupon.id`，系统校验用户归属、未使用、未过期和门槛金额。
4. 支付金额计算：核销成功后计算 `coupon_discount` 和 `final_amount`，支付单使用 `final_amount`。
5. 失败恢复：Redis 扣库存失败、MQ 发送失败、消费者确认失败时恢复用户券状态。
6. 超时恢复：待支付订单超时取消时恢复库存、购买标记和用户券状态，避免营销资产异常损耗。

这里的 `CreateSeckillOrderRequest.coupon_id` 表示用户券实例 ID，而不是券模板 ID。

## 缓存一致性策略

项目区分普通读缓存和秒杀库存缓存：

- 活动信息、商品详情、商品列表采用 Cache Aside。
  - 读：先查 Redis，未命中查 DB，再回填 Redis。
  - 写：后台更新 DB 成功后，主动删除活动缓存、商品详情缓存和商品列表缓存；必要时重新预热。
- 秒杀库存不采用“DB 更新后删除缓存”的普通模式。
  - 活动开始前预热 Redis 库存。
  - 下单时 Redis 原子预扣库存和用户购买标记。
  - Kafka 消费者异步创建订单并扣减 MySQL 库存。
  - 失败、取消、超时通过回滚和补偿恢复 Redis/MySQL 状态。

后台更新活动或商品时提供专门写入口：

- `UpdateSeckillActivity`：更新活动 DB 后删除当前活动缓存和活动商品列表缓存，可选重新预热。
- `UpdateSeckillProduct`：更新商品 DB 和秒杀 SKU 后删除商品详情缓存和活动商品列表缓存，并同步 Redis 秒杀库存，可选重新预热。

## 分布式边界处理

项目不使用跨 Redis、Kafka、MySQL 的分布式事务，而是把交易链路拆成可恢复的阶段：

1. 请求阶段：限流 + 请求幂等，防止重复提交放大下游压力。
2. 预占阶段：Redis 原子扣减库存并写入用户购买标记，同时写入 `PendingReservation` 作为补偿凭证。
3. 消息阶段：Kafka 发送失败时立即删除 pending、回滚 Redis 库存、购买标记和用户券。
4. 确认阶段：消费者在 MySQL 事务中创建订单、写收货快照、扣减 MySQL 库存。
5. 失败阶段：消费多次失败进入死信，并触发 `RollbackSeckillReservation` 回滚 Redis 和用户券。
6. 悬挂阶段：补偿任务扫描长期 pending 且 DB 未落单的预占记录，恢复 Redis 库存、购买标记和用户券。
7. 超时阶段：延迟队列取消待支付订单，恢复 MySQL/Redis 库存和用户券。

缓存雪崩、击穿、穿透的处理：

- 雪崩：商品详情、列表、活动缓存写入时添加随机 TTL 抖动；预热分批执行，避免集中写入和集中失效。
- 击穿：商品详情和当前活动缓存重建使用分布式锁，锁使用 token 释放，避免锁过期后误删其他实例的锁。
- 穿透：商品详情查询前使用 Bloom Filter 过滤不存在的活动商品；当前活动不存在时写短 TTL 空值。
